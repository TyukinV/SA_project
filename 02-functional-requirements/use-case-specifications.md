## 1. Введение

Документ содержит детализированные описания основных прецедентов (Use Cases) системы бронирования отелей. Каждый сценарий описывает взаимодействие между актором и системой для достижения конкретной бизнес-цели.

Описания построены по единому шаблону, включающему:
- **ID и название**
- **Акторы** (участники)
- **Предусловия** (что должно быть верно до начала)
- **Триггер** (событие, инициирующее сценарий)
- **Основной поток** (успешный путь)
- **Альтернативные потоки** (исключения, ошибки, вариации)
- **Постусловия** (состояние системы после успешного завершения)

## 2. Список акторов

| Актор | Описание |
| :--- | :--- |
| **Гость** | Пользователь, который ищет номера, создаёт и оплачивает брони, просматривает статус, отменяет бронь. |
| **Администратор (Ресепшн)** | Сотрудник отеля, выполняющий заселение и выселение гостей, управляющий физическим статусом номеров. |
| **Менеджер** | Сотрудник, ответственный за ручное согласование заявок, управление ценами и генерацию отчётов. |
| **Система (Scheduler)** | Автоматизированный компонент, инициирующий события по таймеру (таймаут оплаты, No-Show). |
| **Платежный шлюз** | Внешняя система, обрабатывающая платежи и отправляющая вебхуки. |

## 4. Детальные спецификации ключевых Use Case

### UC-01: Найти доступные номера

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-01 |
| **Название** | Найти доступные номера |
| **Акторы** | Гость |
| **Предусловия** | Гость находится на странице поиска. |
| **Триггер** | Гость нажимает кнопку «Найти». |

**Основной поток:**
1. Гость вводит даты заезда и выезда, количество гостей.
2. Система проверяет корректность дат (заезд не раньше сегодня, выезд позже заезда).
3. Система выполняет запрос к `inventory_calendar` и `rooms`, фильтруя номера, доступные на все указанные даты, с учётом вместимости.
4. Система возвращает список номеров с их характеристиками (тип, цена за ночь, итоговая стоимость, удобства).

**Альтернативные потоки:**
- **A1 (Нет доступных номеров):** Система показывает сообщение «Нет свободных номеров на выбранные даты» и предлагает изменить даты.
- **A2 (Некорректные даты):** Если дата заезда раньше сегодня или выезд раньше заезда, система показывает ошибку.

**Постусловия:** Гость видит список доступных номеров.

### UC-02: Забронировать номер

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-02 |
| **Название** | Забронировать номер |
| **Акторы** | Гость, Система |
| **Предусловия** | Гость выбрал номер из результатов поиска (UC-01). |
| **Триггер** | Гость нажимает «Забронировать» на странице номера. |

**Основной поток:**
1. Гость заполняет контактные данные (имя, email, телефон) и опционально особые пожелания.
2. Система проверяет, что номер всё ещё доступен на выбранные даты.
3. Система **блокирует** номер в календаре (устанавливает `is_available = false` и временный `booking_id`) и создаёт бронь со статусом `PENDING` и `expires_at = now + 15 минут`.
4. Система возвращает идентификатор брони и перенаправляет гостя на оплату (или предоставляет ссылку на оплату).

**Альтернативные потоки:**
- **A1 (Номер уже недоступен):** Если за время заполнения данных номер забронировал другой гость, система показывает сообщение «Номер уже забронирован» и предлагает выбрать другой.
- **A2 (Ошибка валидации):** Если обязательные поля не заполнены или email некорректен, система просит исправить данные.

**Постусловия:** Бронь создана со статусом `PENDING`, номер заблокирован на 15 минут.

### UC-03: Оплатить бронь

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-03 |
| **Название** | Оплатить бронь |
| **Акторы** | Гость, Платежный шлюз, Система |
| **Предусловия** | Бронь существует со статусом `PENDING` и не истекла. |
| **Триггер** | Гость переходит на страницу оплаты (из UC-02 или по ссылке). |

**Основной поток (асинхронный с вебхуком):**
1. Система создаёт платёжную сессию во внешнем шлюзе (передаёт сумму, `return_url`, `webhook_url`).
2. Система перенаправляет гостя на страницу шлюза.
3. Гость вводит данные карты и подтверждает платёж.
4. Шлюз обрабатывает транзакцию и отправляет **вебхук** на `webhook_url` системы.
5. Система получает вебхук, проверяет подпись и `timestamp`, обновляет статус платежа на `COMPLETED`, брони на `CONFIRMED`, фиксирует блокировку календаря.
6. Система отправляет гостю подтверждение по email.
7. Гость возвращается на сайт, видит статус «Подтверждено».

**Альтернативные потоки:**
- **A1 (Отказ платежа):** Шлюз присылает вебхук со статусом `FAILED`. Система обновляет платеж на `FAILED`, бронь остаётся `PENDING`. Гость видит сообщение об ошибке и может повторить оплату.
- **A2 (Истечение таймаута):** Если гость не оплатил в течение 15 минут, Scheduler переводит бронь в `EXPIRED`, освобождает календарь. Гость получает уведомление о необходимости повторить поиск.
- **A3 (Потеря вебхука):** Scheduler опрашивает шлюз для сверки статуса транзакций с `PENDING` старше 15 минут. При обнаружении `SUCCEEDED` подтверждает бронь.

**Постусловия:** Платёж завершён, бронь подтверждена (или отклонена/истекла).

### UC-06: Заселить гостя (Check-in)

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-06 |
| **Название** | Заселить гостя |
| **Акторы** | Администратор, Система |
| **Предусловия** | Бронь существует со статусом `CONFIRMED`. Текущая дата соответствует дате заезда. |
| **Триггер** | Гость прибыл в отель, администратор находит его бронь. |

**Основной поток:**
1. Администратор ищет бронь по имени, номеру брони или паспорту.
2. Система отображает детали брони.
3. Администратор проверяет документы гостя и нажимает «Заселить».
4. Система меняет статус брони на `CHECKED_IN`, генерирует ключ-карту (или документы) и уведомляет службу уборки (опционально).
5. Администратор выдаёт ключ гостю.

**Альтернативные потоки:**
- **A1 (Бронь не подтверждена):** Если статус `PENDING` или `EXPIRED`, система не даёт заселить и просит сначала оплатить/подтвердить.
- **A2 (Номер физически недоступен):** Если `rooms.physical_status = MAINTENANCE` или `DIRTY`, система блокирует заселение и предлагает дождаться уборки/ремонта.

**Постусловия:** Гость заселён, статус брони `CHECKED_IN`.

### UC-07: Выселить гостя (Check-out)

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-07 |
| **Название** | Выселить гостя |
| **Акторы** | Администратор, Система |
| **Предусловия** | Бронь со статусом `CHECKED_IN`. |
| **Триггер** | Гость сообщает о выезде. |

**Основной поток:**
1. Администратор находит бронь гостя.
2. Система показывает дополнительные услуги (мини-бар, прачечная) для включения в счёт.
3. Администратор добавляет услуги (если есть), нажимает «Выезд».
4. Система пересчитывает итоговую сумму, меняет статус брони на `CHECKED_OUT`, освобождает календарь, меняет физический статус номера на `DIRTY` и создаёт задачу для горничной.
5. Система отправляет гостю финальный чек на email.

**Альтернативные потоки:**
- **A1 (Ранний выезд):** Если гость выезжает раньше запланированной даты, система пересчитывает стоимость за фактическое количество ночей и делает возврат переплаты (если была).
- **A2 (No-Show):** Если гость не заехал в день заезда, ночной Scheduler переводит бронь в `CANCELLED` с пометкой No-Show, освобождает календарь и применяет штраф.

**Постусловия:** Гость выписан, номер свободен для новых броней.

### UC-11: Согласовать заявку (ручное согласование)

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-11 |
| **Название** | Согласовать заявку |
| **Акторы** | Менеджер, Система |
| **Предусловия** | Бронь создана со статусом `PENDING_APPROVAL` (требует ручного согласования). |
| **Триггер** | Менеджер видит новую задачу в списке заявок. |

**Основной поток:**
1. Менеджер открывает заявку, изучает детали (даты, гости, цена, особые пожелания).
2. При необходимости менеджер корректирует цену или условия.
3. Менеджер выбирает действие:
   - **Утвердить:** система меняет статус на `CONFIRMED`, фиксирует `approved_by = ID менеджера`, отправляет уведомление гостю.
   - **Отклонить:** система меняет статус на `REJECTED`, сохраняет причину отклонения (поле `comment`), отправляет уведомление гостю.

**Альтернативные потоки:**
- **A1 (Эскалация):** Если менеджер не назначен в течение 1 часа, система эскалирует заявку администратору (уведомление).
- **A2 (Отмена гостем):** Если гость отменяет бронь до принятия решения, система переводит в `CANCELLED` и убирает задачу у менеджера.

**Постусловия:** Заявка либо подтверждена, либо отклонена.
