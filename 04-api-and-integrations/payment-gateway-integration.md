## 1. Назначение
 
Документ описывает взаимодействие **внутренней системы бронирования (HBS)** с **внешним платежным шлюзом** для проведения онлайн-оплаты бронирований. Мы используем провайдера, поддерживающего асинхронные вебхуки (например, Stripe, ЮKassa, Adyen).
 
---
 
## 2. Общий поток взаимодействия
 
1. **Создание платежа:** HBS отправляет запрос на создание платежной сессии, получает `payment_url` и `transaction_id`.
2. **Перенаправление клиента:** HBS возвращает ссылку клиенту, клиент переходит на страницу шлюза.
3. **Оплата:** Клиент вводит данные карты на стороне шлюза.
4. **Вебхук (асинхронно):** Шлюз присылает результат транзакции на заранее переданный `webhook_url`.
5. **Подтверждение:** HBS обрабатывает вебхук, обновляет статусы брони и платежа.
6. **Fallback (опрос):** HBS периодически опрашивает шлюз для подтверждения статуса, если вебхук не пришёл.
---
 
## 3. API внешнего шлюза (запросы от HBS)
 
### 3.1. Создание платежа (`POST /v1/payments`)
 
**Назначение:** Создать платёжную сессию для конкретной брони.
 
> **Важно:** запрос должен включать заголовок `Idempotency-Key` (например, `booking_id`-UUID), чтобы шлюз гарантировал создание только одного платежа при повторных вызовах из-за таймаутов.
 
**Запрос (от HBS к шлюзу):**
 
```http
POST https://payment-gateway.example.com/v1/payments
Content-Type: application/json
Authorization: Bearer {api_key}
Idempotency-Key: {уникальный_ключ}
```
 
**Тело запроса:**
 
```json
{
  "amount": 750000,
  "currency": "RUB",
  "description": "Бронирование отеля HBS-12345 (заезд 2026-08-10)",
  "return_url": "https://hotel-booking.example.com/payment/result",
  "webhook_url": "https://hotel-booking.example.com/webhook/payment",
  "metadata": {
    "booking_id": "12345"
  }
}
```
 
| Поле | Тип | Обязательное | Описание |
| :--- | :--- | :--- | :--- |
| `amount` | integer | Да | Сумма платежа в минимальных единицах валюты (копейки/центы). Например, 7500.00 RUB = `750000`. |
| `currency` | String | Да | Трёхбуквенный код валюты (например, `RUB`, `USD`). |
| `description` | String | Да | Описание транзакции для клиента. |
| `return_url` | String | Да | URL, на который клиент будет перенаправлен после оплаты (независимо от статуса). |
| `webhook_url` | String | Да | URL, на который шлюз пришлёт асинхронное уведомление о статусе. |
| `metadata` | Object | Нет | Дополнительные данные (например, `booking_id`). |
 
**Ответ (от шлюза к HBS):**
 
```json
{
  "transaction_id": "tr_abc123xyz",
  "payment_url": "https://payment-gateway.example.com/pay/tr_abc123xyz",
  "status": "pending",
  "created_at": "2026-08-06T10:15:30Z"
}
```
 
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `transaction_id` | String | Уникальный идентификатор транзакции в системе шлюза. |
| `payment_url` | String | Ссылка, на которую нужно перенаправить клиента. |
| `status` | String | Начальный статус — `pending`. |
| `created_at` | String | Дата создания платежа в ISO 8601. |
 
### 3.2. Проверка статуса платежа (`GET /v1/payments/{transaction_id}`)
 
**Назначение:** Запросить актуальный статус транзакции (используется для fallback-опроса).
 
**Запрос:**
 
```http
GET https://payment-gateway.example.com/v1/payments/tr_abc123xyz
Authorization: Bearer {api_key}
```
 
**Ответ (успешный платёж):**
 
```json
{
  "transaction_id": "tr_abc123xyz",
  "status": "succeeded",
  "amount": 750000,
  "currency": "RUB",
  "paid_at": "2026-08-06T10:17:45Z"
}
```
 
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `transaction_id` | String | Уникальный идентификатор транзакции. |
| `status` | String | Возможные значения: `pending`, `succeeded`, `failed`, `canceled`. |
| `amount` | Integer | Сумма в копейках. |
| `currency` | String | Код валюты. |
| `paid_at` | String | Дата и время успешного платежа (если есть). |
 
**Ответ (отказ):**
 
```json
{
  "transaction_id": "tr_abc123xyz",
  "status": "failed",
  "error_code": "insufficient_funds",
  "error_message": "Недостаточно средств на карте",
  "amount": 750000,
  "currency": "RUB"
}
```

## 4. Входящий вебхук (от шлюза к HBS)
 
### 4.1. Обработка уведомления (`POST /webhook/payment`)
 
Шлюз асинхронно отправляет `POST`-запрос на указанный `webhook_url` с деталями статуса.
 
**Пример тела запроса (успех):**
 
```json
{
  "transaction_id": "tr_abc123xyz",
  "status": "succeeded",
  "amount": 750000,
  "currency": "RUB",
  "paid_at": "2026-08-06T10:17:45Z",
  "metadata": {
    "booking_id": "12345"
  },
  "signature": "sha256=...",
  "timestamp": 1638795456
}
```
 
**Пример тела запроса (отказ):**
 
```json
{
  "transaction_id": "tr_abc123xyz",
  "status": "failed",
  "error_code": "insufficient_funds",
  "error_message": "Недостаточно средств на карте",
  "metadata": {
    "booking_id": "12345"
  },
  "signature": "sha256=...",
  "timestamp": 1638795456
}
```
 
**Поле `signature`:** вычисляется на основе секретного ключа, тела запроса и `timestamp` (HMAC-SHA256). HBS проверяет подпись и актуальность `timestamp` (не старше 5 минут), чтобы защититься от replay-атак.
 
**Ответы HBS на вебхук:**
 
- **200 OK** — если вебхук обработан успешно (статус обновлён) ИЛИ это дубликат (платёж уже имеет такой `transaction_id`) ИЛИ подпись невалидна (логируем, но отвечаем 200, чтобы не раскрывать информацию злоумышленнику).
- **5xx** (например, `503 Service Unavailable`) — если произошла временная ошибка (БД недоступна, очередь переполнена) — в этом случае шлюз должен повторить отправку вебхука через некоторое время.
---
 
## 5. Идемпотентность и защита от дублей
 
- **Исходящие запросы к шлюзу:** каждый запрос к `POST /v1/payments` должен включать заголовок `Idempotency-Key`, уникальный для каждой попытки создания платежа. В качестве ключа рекомендуется использовать `booking_id` + случайный суффикс или просто UUID. При повторной отправке с тем же ключом шлюз должен вернуть результат первого запроса (не создавая новый платёж).
- **Входящие вебхуки:** дубликаты обрабатываются идемпотентно по `transaction_id` (UNIQUE-ограничение в БД). При получении повторного вебхука с тем же `transaction_id` HBS возвращает `200 OK` и не меняет статус (если он уже финальный).
---
 
## 6. Тайм-ауты и повторные попытки
 
- Время ожидания ответа от шлюза при создании платежа: не более 5 секунд. При тайм-ауте HBS повторяет запрос **с тем же** `Idempotency-Key` до 3 раз с экспоненциальной задержкой.
- **Fallback-опрос:** Scheduler запускается каждые 10 минут и выбирает платежи со статусом `PENDING`, созданные более 15 минут назад. HBS отправляет запрос `GET /v1/payments/{transaction_id}` для сверки статуса.
- Если статус изменился (`succeeded` или `failed`), HBS обновляет платёж и бронь соответствующим образом.
- При получении временной ошибки от шлюза (5xx) HBS повторяет запрос с тем же `Idempotency-Key`.
---
 
## 7. Безопасность
 
- Все запросы к шлюзу используют Bearer Token (API-ключ), который хранится в защищённом секрете (Secrets Manager / Vault).
- Вебхуки защищены HMAC-подписью с включением `timestamp` для защиты от replay-атак. HBS проверяет подпись и актуальность `timestamp` (не старше 5 минут).
- Данные карт никогда не проходят через HBS (все платежи и ввод данных происходят на стороне шлюза), что снижает требования к сертификации PCI DSS.
---
 
## 8. Схема базы данных (связь с платежами)
 
В таблице `payments` хранятся поля:
 
- `gateway_transaction_id` — уникальный идентификатор шлюза.
- `status` — внутренний статус (`PENDING`, `COMPLETED`, `REFUNDED`, `FAILED`).
- `amount` — сумма в копейках.
- `currency` — код валюты.
- `payment_method`, `created_at`, `updated_at` и т.д.
Дополнительно, в `booking_events` фиксируются изменения статуса платежа (для аудита).
 
---
 
## 9. Примеры обработки ошибок
 
| Ситуация | Действие HBS |
| :--- | :--- |
| Шлюз не отвечает при создании платежа | Повторить запрос до 3 раз с экспоненциальной задержкой. При неудаче — вернуть ошибку клиенту. |
| Вебхук пришёл с `status=failed` | Обновить платёж в `FAILED`, бронь остаётся `PENDING`. Клиент видит сообщение об ошибке. |
| Вебхук пришёл с `status=succeeded`, но бронь уже отменена или истекла | Платёж фиксируется как `COMPLETED`, но бронь не подтверждается. Система инициирует автоматический возврат средств (если API шлюза поддерживает возвраты) и создаёт задачу для финансового отдела с пометкой о необходимости ручного контроля. SLA на обработку задачи — 24 часа. Гость получает уведомление о том, что средства будут возвращены. |
| Повторный вебхук (дубль) | Возвращаем `200 OK`, не меняем статус (идемпотентность). |
| Временная ошибка при обработке вебхука (например, БД недоступна) | Возвращаем `503 Service Unavailable`, чтобы шлюз повторил доставку. |
