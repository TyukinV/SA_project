## 1. Назначение документа

Настоящий документ является базовым техническим заданием на разработку информационной системы для автоматизации процессов бронирования, управления номерным фондом и ценообразованием в отелях малого и среднего бизнеса.

Документ определяет:
- Объект автоматизации и цели создания системы.
- Терминологическую базу проекта.
- Общую структуру системы и принципы ее построения.

*Примечание: Детальные функциональные требования, бизнес-процессы и модели данных вынесены в отдельные артефакты портфолио (см. папки `02_Functional_Requirements` и `03_Diagrams`).*

## 2. Введение (Общие сведения)

### 2.1. Краткая характеристика объекта автоматизации
Объектом автоматизации является **операционная деятельность отеля** (с номерным фондом до 100 единиц), включающая следующие бизнес-процессы:
- Обработка запросов на бронирование (онлайн и телефонные звонки).
- Ведение календаря занятости номеров.
- Расчет финальной стоимости проживания с учетом сезонных коэффициентов и дополнительных услуг.
- Формирование отчетности по загрузке и выручке.

В настоящий момент учет ведется с помощью Excel-таблиц, что приводит к **высокому риску ошибок персонала**, отсутствию прозрачной аналитики и прямым финансовым потерям.

### 2.2. Основание для разработки
Основанием для разработки служит стратегическая необходимость отеля в цифровой трансформации.
### 2.3. Цели и задачи создания системы
| № | Цель | Задачи системы |
| :--- | :--- | :--- |
| 1 | Исключить двойные продажи номеров (овербукинг) | Реализовать атомарную блокировку номера на время оплаты (паттерн Pessimistic/Optimistic Lock). |
| 2 | Сократить время подтверждения брони | Предоставить клиенту онлайн-форму с мгновенным расчетом цены и автоподтверждением после оплаты. |
| 3 | Автоматизировать ценообразование | Внедрить модуль динамических цен с гибкими правилами (день недели, сезон, длина проживания). |
| 4 | Повысить лояльность гостей | Организовать автоматическую рассылку статусов бронирования и напоминаний. |

## 3. Термины и определения (Glossary / Терминология)

Для единообразного понимания требований и исключения двусмысленностей в проекте используются следующие термины:

| Термин | Определение |
| :--- | :--- |
| **Номерной фонд** | Совокупность всех номеров отеля, доступных для продажи или обслуживания. |
| **Бронирование** | Гарантированное закрепление конкретного номера (или типа номера) за гостем на определенные даты. |
| **Овербукинг** | Ситуация, при которой система или менеджер продали номер, который физически уже занят другим гостем. Критическая ошибка, которую MVP должен исключить на 100%. |
| **Ноу-шоу (Незаезд)** | Ситуация, когда гость забронировал номер, не отменил бронь и не заехал в установленный день заезда. |
| **Раннее заселение** | Заселение гостя раньше стандартного времени (например, до 14:00). |
| **Поздний выезд** | Выезд гостя позже стандартного времени (например, после 12:00), часто с доплатой. |
| **Минимальная длина проживания** | Ограничение, запрещающее бронировать номер на срок меньше установленного количества ночей (например, в новогодние праздники MinLOS = 3 ночи). |
| **Статус номера** | Текущее физическое состояние номера: *Доступен (Available)*, *Занят (Occupied)*, *На уборке (Dirty)*, *На ремонте (Out of Order)*. |
| **Платежный шлюз** | Внешняя система (агрегатор), через которую происходит списание денежных средств с карты гостя и зачисление их отелю. |
| **Жизненный цикл бронирования** | Последовательность смены состояний: *Создано → Ожидает оплаты → Оплачено → Активно (Заезд) → Завершено (Выезд) / Отменено*. |

## 4. Общая структура системы

В рамках данного ТЗ определяется, что система имеет **микросервисный потенциал, но в MVP реализуется как модульный монолит** (для упрощения деплоя и экономии ресурсов отеля). 

### 4.1. Логическая структура (Функциональные блоки)
Система логически делится на следующие функциональные подсистемы (блоки):

| № | Блок | Назначение |
| :--- | :--- | :--- |
| **1** | **Блок управления номерным фондом** | CRUD-операции над номерами, управление типами номеров (Люкс, Стандарт), изменение статусов (Уборка/Занят). |
| **2** | **Блок ценообразования** | Хранение базовых цен, применение динамических правил (скидки, наценки), расчет итоговой стоимости бронирования. |
| **3** | **Блок бронирования (Ядро системы)** | Основной сервис, отвечающий за создание заказа, блокировку номера, связь с платежами и управление таймаутами. |
| **4** | **Блок управления гостями (CRM)** | Хранение паспортных данных, контактов, истории заездов, черных списков. |
| **5** | **Блок уведомлений** | Асинхронная отправка писем (SMTP) и SMS через внешние брокеры/провайдеров. |
| **6** | **Блок отчетности** | Генерация стандартных аналитических отчетов (загрузка, выручка, популярность номеров). |

### 4.2. Физическая структура (Развертывание)
На уровне инфраструктуры (Deployment) система представляет собой:

- **Frontend-сервер:** Отдает статику (React-приложение) для работы администраторов и страницу публичного сайта для гостей.
- **Backend-сервер (Application Server):** Обрабатывает REST API-запросы, содержит бизнес-логику.
- **База данных:** PostgreSQL (единственное хранилище данных, обеспечивающее ACID для транзакций бронирования).
- **Cache-слой:** Redis (используется для хранения временных блокировок и сессий, чтобы не нагружать основную БД).
- **Интеграционная шина:** В MVP — прямые REST-запросы к платежному шлюзу.

### 4.3. Взаимодействие с внешними системами
На этапе ТЗ мы выделяем 2 обязательных внешних контура:

1.  **Платежная система (ЮKassa):** API для создания платежных интентов и подтверждения факта оплаты.
2.  **Email/SMS-провайдер:** Сервис для отправки транзакционных писем (подтверждения, напоминания о выезде).

## 5. Требования к надежности и информационной безопасности

- **Надежность:** Система должна сохранять работоспособность в часы пиковой нагрузки (20:00 - 22:00, время активного бронирования). Допустимое время восстановления после критического сбоя — не более 30 минут.
- **Безопасность:** 
  - Все соединения с платежным шлюзом должны проходить по протоколу TLS 1.3.
  - Пароли пользователей и данные банковских карт (CVV) не хранятся в системе (используется токенизация со стороны платежного шлюза).
  - Доступ к панели администратора строго по ролевой модели (Администратор, Менеджер, Наблюдатель).
