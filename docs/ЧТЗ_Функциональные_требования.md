## 3. Сценарии использования 

В данном разделе описаны ключевые потоки событий для самого важного функционала — бронирования.
### UC-01: Забронировать номер (Основной поток)

| Элемент | Описание |
| :--- | :--- |
| **ID** | UC-01 |
| **Название** | Бронирование номера с онлайн-оплатой |
| **Акторы** | Гость (Клиент), Платежный шлюз (внешняя система) |
| **Предусловия** | Гость авторизован (или гость без регистрации). Выбраны даты заезда/выезда. |
| **Триггер** | Гость нажимает кнопку «Забронировать» после заполнения контактных данных. |

#### Базовый поток 
1. Система получает запрос на бронирование конкретного номера на выбранные даты.
2. Система **блокирует** номер в БД (устанавливает статус «Ожидает оплаты») на 15 минут. *(Снятие блокировки обрабатывается таймером).*
3. Система создает запись «Бронирование» со статусом `PENDING_PAYMENT` и генерирует платежную ссылку.
4. Система перенаправляет Гостя на страницу платежного шлюза.
5. Гость вводит данные карты и подтверждает оплату.
6. Платежный шлюз возвращает в систему Webhook-уведомление об успешной оплате.
7. Система меняет статус бронирования на `CONFIRMED` (Подтверждено).
8. Система отправляет гостю на email подтверждение с деталями заезда.
9. Статус доступности номера в календаре (inventory_calendar.is_available) меняется на false (номер зарезервирован на указанные даты). В пользовательском интерфейсе этот статус отображается как «Занят» или «Забронирован»..

#### Альтернативный поток (A-1: Истек таймаут оплаты)
1. Гость не оплачивает бронь в течение 15 минут.
2. Системный таймер (Scheduler) срабатывает и переводит бронь в статус `EXPIRED` (Просрочена).
3. Система **снимает блокировку** с номера (номер возвращается в пул «Доступен»).
4. Гость получает уведомление: «Время сессии истекло, повторите поиск».

#### Альтернативный поток (A-2: Отказ платежного шлюза)
1. Платежный шлюз возвращает ошибку (недостаточно средств, неверный CVV).
2. Система не меняет статус бронирования (остается `PENDING_PAYMENT`).
3. Система показывает гостю сообщение об ошибке и предлагает повторить оплату или использовать другую карту.
4. Таймер (15 мин) продолжает работать, давая гостю шанс исправить данные.

#### Постусловия (Успех)
- Бронь имеет статус `CONFIRMED`.
- Номер зарезервирован в системе на указанные даты.
- Деньги заблокированы/списаны со счета гостя.

## 4. Нефункциональные требования


| Категория | Требование | Метрика / Критерий приемки |
| :--- | :--- | :--- |
| **Производительность** | Поиск доступных номеров должен происходить мгновенно, даже при высоких нагрузках. | Время отклика API поиска < 500 мс при нагрузке до 1000 одновременных запросов (RPS). |
| **Производительность** | Обработка платежа (с учетом внешнего шлюза) не должна создавать ощущение «зависания». | Время ожидания ответа от платежного шлюза до возврата в интерфейс < 3 секунд (с таймаутом 5 сек). |
| **Доступность** | Система должна работать практически без перебоев в пиковые часы (вечернее время). | Доступность (SLA) = 99.5% (допустимое время простоя ~3,5 часа в месяц). |
| **Безопасность** | Конфиденциальные данные гостей и платежей защищены. | Никакие данные карт (PAN, CVV) не хранятся в БД HBS. Используется токенизация шлюза. Обязательное шифрование TLS 1.3. |
| **Юзабилити** | Интерфейс поиска и бронирования интуитивен. | Количество шагов до успешного бронирования — не более 5 кликов. Адаптивная верстка для мобильных устройств. |
| **Отказоустойчивость** | Сбои внешних сервисов не должны ломать ядро системы. | В случае недоступности платежного шлюза, система корректно показывает ошибку, не теряя данные бронирования. |
| **Масштабируемость** | Архитектура позволяет расширять номерной фонд. | Добавление нового отеля (до 100 номеров) не требует переписывания ядра, только добавление записей в БД. |

## 5. Бизнес-правила и ограничения 


1.  **Правило минимальной длины проживания (MinLOS):** Если отель выставил MinLOS = 3 ночи на новогодние праздники, система должна автоматически блокировать бронирование на 1 или 2 ночи (кнопка "Забронировать" неактивна или выдается ошибка).
2.  **Политика отмены:**
    - При отмене более чем за 3 дня до заезда — возврат 100%.
    - При отмене менее чем за 3 дня — возврат 0% (штраф).
3.  **Правило овербукинга (строго):** Никто и никогда не может изменить статус номера на `OCCUPIED`, если на него есть пересекающееся бронирование со статусом `CONFIRMED`. Это проверяется на уровне БД (триггер или программная проверка).
4.  **Время заезда/выезда:** Система считает "ночью" период с 14:00 текущего дня до 12:00 следующего дня. Если гость указывает выезд 5-го числа, последняя ночь оплачивается за 4-е число.

## 6. Требования к логированию и мониторингу

- Логировать **все** изменения статуса бронирования (кто, когда, с какого на какой статус). Это нужно для аудита и разбора спорных ситуаций с гостями.
- Логировать все входящие Webhook-и от платежного шлюза с тело запроса (для отладки проблем с деньгами).
- Предусмотреть метрику в системе мониторинга (например, Prometheus): `Количество активных блокировок (Pending)`. Если их становится > 100, это сигнал о высокой нагрузке.

---

## 7. Критерии приемки для ключевого сценария UC-01


1. **AC-01.1:** Система не дает создать бронь, если выбранный номер уже имеет пересекающееся бронирование со статусом `CONFIRMED`.
2. **AC-01.2:** Время блокировки (таймаут) выставляется ровно 15 минут и сбрасывается при каждом повторном запросе оплаты.
3. **AC-01.3:** После успешного получения Webhook-а статус брони меняется на `CONFIRMED` в течение 5 секунд.
4. **AC-01.4:** Гость получает письмо на указанный email не позднее, чем через 1 минуту после успешной оплаты.
