## 1. Назначение

Проверить, что система **гарантированно исключает овербукинг** — ситуацию, при которой на один номер на одни и те же даты создаются две пересекающиеся брони.

**Цель теста:** убедиться, что бизнес-цель **BG-01** (снижение овербукинга до 0%) достигается на уровне БД и приложения, включая конкурентные запросы, частичные пересечения и попытки обхода через прямую вставку в БД.

**Критичность:** это ключевое требование MVP. Провал этого теста означает провал всего проекта.

---

## 2. Предусловия

| Условие | Значение |
| :--- | :--- |
| В БД | 10 номеров: 5 STANDARD, 3 DELUXE, 2 SUITE |
| Номер №101 | STANDARD, capacity = 2 |
| Календарь | Номер №101 свободен на 10–15 августа 2026 |
| Активные брони | Отсутствуют на выбранные даты |
| Backend | Доступен, БД подключена, транзакции настроены |
| Уникальный индекс | `idx_inventory_unique_booking` создан на `(room_id, calendar_date) WHERE is_available = false` |

## 3. Сценарии

### Сценарий 1: Конкурентное бронирование (два гостя одновременно)

```gherkin
Функция: Защита от овербукинга
  Сценарий: Два гостя одновременно бронируют один номер
    Дано гость A и гость B одновременно открыли страницу номера №101
    И оба выбрали даты 10–13 августа 2026
    Когда гость A нажимает "Забронировать" в момент T
    И гость B нажимает "Забронировать" в момент T + 10 мс
    Тогда только одна бронь создаётся успешно
    И вторая бронь получает ошибку 409 Conflict
    И сообщение: "Номер уже забронирован на выбранные даты"
    И в inventory_calendar для номера №101 на 10, 11, 12 августа
       существует ровно одна запись с is_available = false
```

---

### Сценарий 2: Полное пересечение дат

```gherkin
Функция: Проверка пересечения дат
  Сценарий: Бронь на те же самые даты
    Дано номер №101 забронирован на даты 10–13 августа
    И бронь имеет статус "CONFIRMED"
    Когда другой гость пытается забронировать на 10–13 августа
    Тогда система возвращает ошибку 409 Conflict
    И сообщение: "Номер недоступен на указанные даты"
    И новая бронь НЕ создаётся
```

---

### Сценарий 3: Частичное пересечение дат

```gherkin
Функция: Проверка пересечения дат
  Сценарий: Брони на пересекающиеся даты
    Дано номер №101 забронирован на даты 10–13 августа
    Когда другой гость пытается забронировать на 12–15 августа
    Тогда система возвращает ошибку 409 Conflict
    И сообщение: "Номер недоступен на указанные даты"
    И в inventory_calendar для номера №101 на 12 августа
       не создаётся вторая запись с is_available = false
```

---

### Сценарий 4: Смежные даты (без пересечения) — успешное бронирование

```gherkin
Функция: Проверка смежных дат
  Сценарий: Бронирование сразу после выезда
    Дано номер №101 забронирован на 10–13 августа (выезд 13-го)
    Когда другой гость бронирует на 13–15 августа (заезд 13-го)
    Тогда бронь создаётся успешно
    И номер доступен на 13, 14 августа
    И в inventory_calendar для номера №101:
      | calendar_date | is_available | booking_id |
      | 2026-08-10    | false        | 123        |
      | 2026-08-11    | false        | 123        |
      | 2026-08-12    | false        | 123        |
      | 2026-08-13    | false        | 456        |
      | 2026-08-14    | false        | 456        |
```

> **Примечание:** ночь с 12 на 13 августа занята первым гостем. Второй заезжает 13-го после 14:00, когда первый уже выехал (до 12:00). Это корректная ситуация, а не пересечение.

---

### Сценарий 5: Пересечение с бронью в статусе PENDING

```gherkin
Функция: Учёт PENDING-броней
  Сценарий: Бронь в статусе PENDING тоже блокирует номер
    Дано номер №101 забронирован на 10–13 августа
    И бронь имеет статус "PENDING" (ожидает оплаты)
    Когда другой гость пытается забронировать на 10–13 августа
    Тогда система возвращает ошибку 409 Conflict
    И сообщение: "Номер недоступен на указанные даты"
```

> **Согласно AC-02.1:** `PENDING` и `PENDING_APPROVAL` удерживают блокировку наравне с `CONFIRMED`.

---

### Сценарий 6: Пересечение с бронью в статусе PENDING_APPROVAL

```gherkin
Функция: Учёт PENDING_APPROVAL-броней
  Сценарий: Заявка на согласовании тоже блокирует номер
    Дано номер №101 забронирован на 10–13 августа
    И бронь имеет статус "PENDING_APPROVAL"
    Когда другой гость пытается забронировать на 10–13 августа
    Тогда система возвращает ошибку 409 Conflict
```

---

### Сценарий 7: Защита на уровне БД (частичный уникальный индекс)

```gherkin
Функция: Защита на уровне БД
  Сценарий: Попытка вставить дубликат напрямую в БД
    Дано в inventory_calendar уже есть запись:
      | room_id | calendar_date | is_available | booking_id |
      | 101     | 2026-08-10    | false        | 555        |
    Когда система пытается вставить новую запись:
      | room_id | calendar_date | is_available | booking_id |
      | 101     | 2026-08-10    | false        | 777        |
    Тогда БД возвращает ошибку unique_violation
    И транзакция откатывается
    И вторая бронь не создаётся
```

---

### Сценарий 8: Отмена освобождает даты для новой брони

```gherkin
Функция: Освобождение календаря при отмене
  Сценарий: После отмены брони номер снова доступен
    Дано номер №101 забронирован на 10–13 августа
    И бронь №123 в статусе "CONFIRMED"
    Когда гость отменяет бронь №123
    Тогда система переводит бронь в "CANCELLED"
    И обновляет inventory_calendar:
      | calendar_date | is_available | booking_id |
      | 2026-08-10    | true         | NULL       |
      | 2026-08-11    | true         | NULL       |
      | 2026-08-12    | true         | NULL       |
    Когда другой гость бронирует на 10–13 августа
    Тогда бронь создаётся успешно
```

---

### Сценарий 9: Гонка «отмена + новое бронирование»

```gherkin
Функция: Конкурентная отмена и бронирование
  Сценарий: Отмена и новая бронь одновременно
    Дано бронь №123 на номер №101, даты 10–13 августа, статус "CONFIRMED"
    Когда гость A отменяет бронь №123 в момент T
    И гость B одновременно бронирует те же даты в момент T + 10 мс
    Тогда либо:
      | Вариант | Результат |
      | A       | Отмена успешна, B создаёт бронь |
      | B       | B получает 409 Conflict, A отменяет успешно |
    И в inventory_calendar не возникает двух пересекающихся блокировок
    И состояние БД консистентно
```

> **Примечание:** тест проверяет, что даже при гонке «освобождение + блокировка» система не создаёт двойную бронь. Допустимы оба исхода, но не допустимо состояние, при котором обе брони активны.

---

## 4. Постусловия

| Состояние | Значение |
| :--- | :--- |
| `inventory_calendar` | Нет двух пересекающихся блокировок для одного номера |
| `idx_inventory_unique_booking` | Не нарушен |
| `bookings` | Все созданные брони имеют консистентные статусы |
| `booking_events` | Зафиксированы все попытки (включая неудачные, если логируется) |
| Счётчик `booking_conflict_total` | Увеличен на количество отклонённых запросов |

## 5. Тестовые данные

### Общие параметры

| Параметр | Значение |
| :--- | :--- |
| room_id | 101 |
| room_type | STANDARD |
| capacity | 2 |
| check_in (бронь A) | 2026-08-10 |
| check_out (бронь A) | 2026-08-13 |
| check_in (бронь B, пересечение) | 2026-08-12 |
| check_out (бронь B, пересечение) | 2026-08-15 |
| check_in (бронь C, смежная) | 2026-08-13 |
| check_out (бронь C, смежная) | 2026-08-15 |

### Ожидаемые записи в `inventory_calendar` (сценарий 1)

```
| room_id | calendar_date | is_available | booking_id |
|---------|---------------|--------------|------------|
| 101     | 2026-08-10    | false        | 123        |
| 101     | 2026-08-11    | false        | 123        |
| 101     | 2026-08-12    | false        | 123        |
```

Ровно **одна** запись на каждую дату. Вторая бронь не создаёт записей.

| 101     | 2026-08-12    | false        | 123        |

## 6. Метрики для мониторинга

| Метрика | Описание | Целевое значение |
| :--- | :--- | :--- |
| `booking_conflict_total` | Количество ошибок 409 | — (информативно) |
| `booking_transaction_deadlocks_total` | Количество deadlock'ов | **0** |
| `booking_creation_duration_seconds` | Время создания брони | p95 < 1 сек |
| `inventory_unique_violation_total` | Срабатывания уникального индекса | — (информативно) |

**Алерт:** если `booking_transaction_deadlocks_total > 0` — требуется разбор (возможна проблема с порядком блокировки строк).

## 7. Критерии приёмки (Definition of Done)

- [ ] Все 9 сценариев проходят на тестовом стенде.
- [ ] Нагрузочный тест: 100 одновременных запросов на один номер → ровно 1 успешная бронь, 99 ошибок 409.
- [ ] Проверено, что частичный уникальный индекс `idx_inventory_unique_booking` создан и работает.
- [ ] Проверено, что попытка вставить дубликат напрямую в БД откатывается.
- [ ] Проверено, что отмена брони освобождает даты для новой брони.
- [ ] Логи содержат `booking_conflict` с полями `room_id`, `check_in`, `check_out`.
- [ ] Покрытие автотестами ≥ 90% для кода блокировки календаря.
